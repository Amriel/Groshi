# Як вносити зміни

Проєкт має два правила, які важливіші за стиль коду.

**1. Кожна зміна доводиться пробою.** У теці `tests/` лежать сценарії на
Playwright: вони відкривають зібраний файл, роблять те саме, що зробила б
людина, і друкують результат. Перед тим як щось лагодити, напишіть пробу,
яка ловить поточну поведінку — інакше нема доказу, що баг був і що він
зник. Приклад із життя проєкту: пробу на привидів скляного шару спершу
прогнали на СТАРІЙ збірці (18 привидів із 24), потім на новій (0).

```bash
node tests/allcheck.mjs        # загальний прохід по вкладках
node tests/gaps.mjs            # зазори між картками на всіх вкладках
```

**2. Коментар пояснює ЧОМУ, а не ЩО.** `// збільшуємо лічильник` — сміття.
`/* Дата угоди мусить знайти СВОЮ точку ряду, а не збігтися з нею: на
тижневих свічках угода між ними давала нуль крапок */` — те, що збереже
час наступному. Якщо рішення викликане реальним випадком — напишіть який.

## Про архітектуру

- `app/app.template.html` — уся браузерна апка одним файлом. Скрипти
  `glassgl.js` і `designer.js` вставляються в нього під час збірки.
- `desktop/build_desktop.py` — вставляє той самий шаблон у Tauri-оболонку,
  замінюючи браузерні заглушки на виклики Rust. Підстановки прив'язані до
  ЯКОРІВ у тексті шаблону і падають з помилкою, якщо якір змінився — це
  навмисно: краще зламана збірка, ніж тиха втрата функції.
- `desktop/src-tauri/src/` — Rust: банк, брокери, котирування, сховище,
  ключі. Мережа й секрети живуть тільки тут.
- `desktop/dist/*.js` — нормалізатори (банк, брокери) і міст до Rust.
  Вони окремими файлами, бо формати виписок міняються частіше за все
  інше, і правити їх треба без перезбирання застосунку.

## Секрети

Власні дані тримайте поза репозиторієм. Ніколи не комітьте виписки XML/CSV,
`*_raw.json`, `state.json`, приватні набори даних, `.env`, ключі, резервні
копії чи тимчасові файли `*.tmp`. `.gitignore` допомагає з новими файлами,
але **не захищає файли, які Git уже відстежує**, і не зупиняє `git add -f`.
Токен Monobank браузерна версія отримує через `MONO_TOKEN`, десктопна —
через Диспетчер облікових даних Windows. Не записуйте токени у файли,
логи, повідомлення чи тексти помилок.

У публічному Git три файли завжди порожні:

- `app/dataset.json` — `[]`;
- `desktop/dist/legacy.json` — `[]`;
- `app/meta.json` — `{"built":"","source":"","n":0}` без додаткових полів.

Для прикладів використовуйте явні підстановки `YOUR_TOKEN_HERE`, порожні
масиви, рахунок `U0000000`, адреси на `example.com`, `example.org` або
`example.net`, шляхи з `USER` чи `username`. Дозволено `.env.example` із
підстановками. Номер картки, що проходить перевірку Luhn, і коректний IBAN
вважаються ризиком навіть у тесті: складайте такі синтетичні значення з
частин безпосередньо в пробі. Винятку для всієї теки `tests/` немає.
Адреси GitHub `users.noreply.github.com`, контрольні суми залежностей,
підписи `.sig` та публічні ключі дозволені; приватні ключі заборонені.

## Перевірка перед комітом

Потрібні Git і Python 3.10 або новіший, додаткових пакетів немає. Запускайте
з кореня репозиторію:

```powershell
python scripts/privacy_check.py
python -m unittest discover -s tests -p test_privacy_check.py -v
git add -- <шляхи-до-змінених-файлів>
python scripts/privacy_check.py --staged
git diff --cached --stat
```

Звичайний режим читає лише відстежувані робочі файли. `--staged` читає
**весь індекс Git** через об’єкти Git: саме майбутній коміт, включно з
новими назвами після перейменування. Незбережена в індексі правка не може
приховати вже підготовлений секрет. Видалені з індексу файли не читаються.
Символічні посилання та підмодулі блокуються, щоб перевірка не читала
зовнішні дані й не створювала хибне відчуття перевіреного вмісту.

При порушенні виводяться лише `шлях:рядок:правило`, без значення секрету.
Код завершення `0` означає успіх, `1` — порушення, `2` — неможливість
перевірки. Після виправлення повторіть `git add` і `--staged`.
Це локальна перевірка відомих ознак, а не гарантія відсутності будь-яких
персональних даних; історію комітів вона не перевіряє.

### Локальний pre-commit hook

Команди нижче ставлять hook лише в цьому репозиторії, без глобальної
конфігурації. Якщо hook уже є, додайте до нього виклик перевірки вручну,
зберігши його наявні дії. Якщо `git config --get core.hooksPath` виводить
шлях, використовуйте чинний механізм hooks замість цього рецепта.

```powershell
git config --get core.hooksPath
$privacyHook = git rev-parse --git-path hooks/pre-commit
if (Test-Path -LiteralPath $privacyHook) { throw 'Hook уже існує: доповніть його вручну.' }
$privacyHookBody = "#!/bin/sh`nexec python scripts/privacy_check.py --staged`n"
[System.IO.File]::WriteAllText([System.IO.Path]::GetFullPath($privacyHook), $privacyHookBody, [System.Text.UTF8Encoding]::new($false))
python scripts/privacy_check.py --staged
```

Для Git Bash/Linux/macOS (також лише за відсутності чинного hook і
`core.hooksPath`):

```bash
hook="$(git rev-parse --git-path hooks/pre-commit)"
test ! -e "$hook" && printf '#!/bin/sh\nexec python3 scripts/privacy_check.py --staged\n' > "$hook" && chmod +x "$hook"
python3 scripts/privacy_check.py --staged
```

Hook можна обійти, тому CI має окремо запускати `python scripts/privacy_check.py`
та наведені вище проби. Перед публікацією перевіряйте також склад коміту.
